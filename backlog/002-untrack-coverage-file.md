# Stop tracking `.coverage` in git so the working tree is clean after a gate run.
REPO: InsightWeaver
STATUS: QUEUED            # QUEUED | IN_PROGRESS | PARKED | DONE | FAILED
ACCEPTANCE: `make check` passes, plus: `git ls-files --error-unmatch .coverage` exits non-zero (the file is no longer tracked); `git status --porcelain` is empty immediately after a fresh `make check` on an otherwise clean tree; and the file still exists on disk afterwards, i.e. it was untracked, not deleted from the developer's machine.
OUT OF SCOPE: Removing `--cov=src`, `--cov-report=term-missing`, or `--cov-report=html` from `addopts` in `pyproject.toml` — coverage on every run is a deliberate choice and this task does not relitigate it. Adding a coverage threshold or a `--cov-fail-under` gate; that is a real idea and it is a different task. Changing the CI coverage job or the Codecov upload. Rewriting git history to purge `.coverage` from past commits — it is a small binary and the cost of a rewrite is not worth it here. Touching `htmlcov/` (already correctly ignored and untracked) or any other entry in `.gitignore`. `src/`, `tests/`, or the database.
LANDMINES: `.coverage` is **both tracked and gitignored** — `.gitignore` L59 lists it, and `git ls-files --error-unmatch .coverage` succeeds anyway, because `.gitignore` has no effect on a file git is already tracking. That is why it has looked ignored while never behaving that way. It is a binary SQLite file: `git diff --stat` shows "Bin 53248 -> 69632 bytes" and every diff is unreviewable, so it has been carried along in unrelated commits (`88e81ae`, `20a3717`, `1fdb5af`). It is rewritten by **every** pytest invocation, not just `make coverage`: `pyproject.toml` `[tool.pytest.ini_options].addopts` includes `--cov=src`, so `make test` and therefore `make check` both rewrite it. `git rm --cached .coverage` will show the file as deleted to anyone who pulls — that is correct and expected, but say so in the commit message so nobody re-adds it. Do **not** use `git rm` without `--cached`; that deletes the local file. Separately, `make clean` already does `find . -type f -name ".coverage" -delete`, so today a `make clean` deletes a tracked file and dirties the tree in the opposite direction — after this change that target becomes correct rather than surprising, which is worth a sentence in the PR. Local `main` is 11 commits ahead of `origin`; do not push. The working tree currently also carries an unrelated uncommitted edit to `src/cli/frames.py` — leave it alone.

Diagnosed 2026-08-24 during Session 2a and recorded as deferred in `~/.claude/setup/SETUP-LOG.md`: "`.coverage` is a **tracked** file rewritten by every `make test`, so the tree is never clean after a gate run. This will produce false 'dirty tree' signals in Sessions 4–6."

That last sentence is the reason this is queued rather than left as a nit. The unattended setup being built around these repos uses "is the working tree clean?" as a signal — a reviewer agent asks what the author actually changed, and an orchestrator decides whether work is finished. In this repo, running the gate guarantees a dirty tree, so that signal is unreliable in exactly the situation it is needed.

The fix:

```
git rm --cached .coverage
git commit -m "stop tracking .coverage; it is a build product regenerated by every pytest run"
```

`.gitignore` L59 already lists it, so nothing else is needed to keep it out from here on. Confirm afterwards that the file is still on disk and that a fresh `make check` leaves `git status` empty.

While confirming: `htmlcov/` is the other coverage output (`--cov-report=html`), and it is already ignored *and* untracked, so it needs nothing. `.coverage` was the only one that slipped through.
